# Plan: §3.6 System Attributes — Virtual Team Skill

---

## §3.6.1 Reliability

**Definition**: Ability of the system to perform its required functions under stated conditions for a specified period of time without failure.

### Mean Time Between Failures (MTBF)
- Virtual Team Skill has no server-side component; there is no daemon, service, or persistent process to fail between invocations.
- "Failure" in this context = a skill invocation that does not produce expected artifacts despite correct operator input and available API.
- Target: ≥ 95% of skill invocations complete successfully on the first try (before any retries), for standard-complexity requirements.
- After automated retry (Layer 1): ≥ 99% of skill invocations produce complete artifact sets.

### Failure Behavior
- **Graceful degradation**: When a single agent fails validation after 3 retries (hard stop), the pipeline halts at that agent. All artifacts generated by preceding agents are preserved on disk. The operator can inspect existing artifacts and resume from the failing agent.
- **No silent failure**: Every failure is explicitly reported with the affected agent name, the missing sections, and the path to the failure log.
- **No data loss on failure**: Artifacts already written by preceding agents are never deleted or overwritten by a failure in a later agent.
- **API call failure (timeout, network error)**: Claude Code surfaces the error to the operator; skill cannot recover automatically; operator must retry the failed command.

### Retry Logic Reliability
- Layer 1 automated retry is deterministic: same validation schema applied every time, same augmented prompt structure used for retry.
- Retry does not use exponential backoff (no need — LLM retry is triggered by structural validation failure, not transient API error).

## §3.6.2 Availability

**Definition**: Degree to which the system is operational and accessible when required for use.

### Uptime SLA
- Not applicable as a traditional SLA — Virtual Team Skill is not a hosted service.
- Availability = Anthropic API availability × Claude Code CLI availability × local machine availability.
- Expected practical availability: whenever the operator's machine and internet connection are available (same as Claude Code's own availability).

### Maintenance Window
- None — no scheduled downtime for a local CLI tool.
- Skill updates (new `.md` file versions) require the operator to update their local repository; no downtime during normal use.

### Session Continuity
- The skill does not require a continuous session to be useful. Each agent invocation is stateless at the API level; state is carried by disk artifacts (NFR-02).
- If Claude Code is closed mid-pipeline: resume by running the next agent command after restart.

### Dependency Availability
- The skill inherits availability from Anthropic API. During Anthropic API outages, the skill is non-functional.
- The skill does not implement retry for API outages — it relies on operator to retry after API restoration.

## §3.6.3 Security

**Definition**: Degree to which the system protects information and data, ensuring authorized access while preventing unauthorized access.

### Authentication & Authorization
- **No in-skill authentication**: Virtual Team Skill does not authenticate operators. Access control is entirely via the local machine's OS file system permissions.
- **Claude Code API authentication**: Handled by Claude Code CLI (API key in local config). Skill does not access, store, or transmit the API key.
- **Multi-user security**: Not applicable in v1 (single-user, local tool). If multiple OS users share a machine, OS-level file permissions control artifact access.

### Encryption
- **Data in transit**: All communication with Anthropic API uses HTTPS/TLS (managed by Claude Code). No plaintext API communication.
- **Data at rest**: Artifacts are stored as unencrypted Markdown files on the local file system. Encryption at rest is the operator's responsibility (OS-level disk encryption, e.g., FileVault on macOS, BitLocker on Windows).
- **No encryption features added by the skill**: Virtual Team Skill does not encrypt artifact files.

### Secret Management
- **Core rule**: No credentials, API keys, tokens, or passwords may appear in any generated artifact (FR-24, FR-27, BR-05).
- **Enforcement**: BA, BE Dev, FE Dev agent instructions explicitly prohibit hardcoding secrets.
- **QA/QC review**: QA/QC agent reviews all code artifacts for hardcoded secrets as part of its compliance check (FR-32).
- **`.env.example`**: BE Dev agent generates `.env.example` listing all required environment variables with placeholder values (not real values).

### Data Transmission Scope
- Only the operator's requirement input and generated artifact content traverse the Anthropic API (for LLM inference).
- No artifact content is transmitted to any other service (NFR-05).
- Operator is responsible for the sensitivity of content they input as requirements.

### Vulnerability Management
- Skill files (`.md` files) contain only text instructions — no executable code that could have injection vulnerabilities.
- Risk: prompt injection in operator input. Mitigation: agents are instructed to follow their role definition; however, prompt injection risks exist for any LLM-based system and cannot be fully eliminated at the skill level.
- Security scanning: not applicable (no compiled code in the skill itself).

## §3.6.4 Maintainability

**Definition**: Degree of effectiveness and efficiency with which the system can be modified to improve it, correct it, or adapt it to changes in environment.

### Skill File Structure
- Each role is a separate `.md` skill file — changes to one role do not affect others.
- Validation schemas (required section lists) should be defined in a dedicated reference file, not embedded in each skill, to allow centralized updates.
- Agent model assignments are specified per-skill; updating a model requires editing the relevant skill file only.

### Code Coverage Requirement
- Not applicable in the traditional sense (no compiled code).
- Equivalent quality gate: every FR in §3.2 must have at least one documented test scenario in the Tester's test plan when the skill itself is tested.

### Deployment / Update Process
- Updates are shipped as new versions of skill `.md` files in the repository.
- Operators pull the latest version via git and the updated skills are immediately available in Claude Code.
- No database migrations, build steps, or deployment pipelines needed.
- Breaking changes (e.g., changing output file structure) must update the `00-overview.md` file map and all downstream skill files that read those paths.

### Dependency Update Policy
- Virtual Team Skill has no package dependencies (no `package.json`, `requirements.txt`, etc.).
- Claude Code and Anthropic API are the only dependencies — operators update Claude Code via their package manager; skill authors must review skill compatibility when Claude Code makes breaking changes.

### Branching Strategy
- Skill development follows the existing repository branching strategy (`feat/{name}` branches, merged to `main` via PR).
- Skill version history is tracked via git.

## §3.6.5 Portability

**Definition**: Degree of effectiveness and efficiency with which a system can be transferred from one hardware or software environment to another.

### Supported Platforms
- Windows 10/11 (PowerShell + Bash via Git Bash)
- macOS 12+ (Zsh / Bash)
- Ubuntu 20.04+ (Bash)
- Future: Any OS that supports Claude Code CLI

### Containerization
- Not applicable to v1 (the skill runs inside Claude Code CLI, which is itself installable on any supported OS).
- No Docker container required or provided.

### Data Export Format
- All artifacts are Markdown (`.md`) and source code files — universally portable text formats.
- No proprietary export format.
- Operators can copy the `projects/{slug}/team/` directory to any location or upload to any Markdown-capable system (Notion, Confluence, GitHub, etc.).

### Installation
- Operator copies skill `.md` files to their Claude Code skills directory (`.claude/skills/` or repository-local `.claude/skills/`).
- No installer, build step, or system package required.

## §3.6.6 Usability

**Definition**: Degree to which the system can be used by specified users to achieve specified goals with effectiveness, efficiency, and satisfaction.

### Learnability
- Each skill command follows a consistent pattern: `/team-{role} [--project {slug}] [--context "{extra}"]`
- Help output for each command should display: what the agent does, what inputs are required, what outputs are produced, and the next step.
- [NEEDS USER INPUT: define `--help` flag behavior for each command — is inline help text provided in the skill?]

### Efficiency
- Full pipeline can be triggered with a single command and zero subsequent interactions in the happy path.
- Per-agent mode allows surgical re-running of single agents without re-executing the entire pipeline.
- Artifact paths are consistent and predictable (`projects/{slug}/team/{role}/`) — operators know where to find outputs without searching.

### Error Message Quality
- All error messages MUST identify: which agent failed, what was expected, what was found, and the exact command to resolve the issue.
- Example: `[BA] ✗ Validation failed — missing sections: [## Business Rules] — run: /team-ba --project {slug} to retry`
- Hard stop messages MUST include the path to the failure log.

### WCAG Compliance
- Not applicable (CLI tool, not a web application).
- CLI output is compatible with screen readers that read terminal output.

### Onboarding
- A README or CLAUDE.md should document: system prerequisites, installation steps, basic usage example (full pipeline + per-agent), and where to find artifacts.

### Max Task-Completion Steps
- To generate a complete artifact set from a requirement: 1 command (`/team "requirement"`) — single step for ACTOR-01 and ACTOR-04
- To run a specific agent: 1 command per agent — linear, no branching menus
- To review outputs: navigate file system to `projects/{slug}/team/` — standard OS file operations
