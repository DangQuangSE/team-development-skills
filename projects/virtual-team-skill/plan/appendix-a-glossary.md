# Plan: Appendix A — Glossary — Virtual Team Skill

All terms used in this SRS that require precise definition to avoid ambiguity. Organized alphabetically.

---

| Term                                            | Definition                                                                                                                                                                                                                                                                   | Related Terms                                   | Source                                                   |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | -------------------------------------------------------- |
| **ADR** (Architecture Decision Record)          | A document that captures a single major architectural decision, structured as: § Context (what situation required a decision), § Decision (what was decided), § Consequences (what trade-offs result). Named sequentially: `ADR-001.md`, `ADR-002.md`, etc.                  | TechLead Phase, Design Freeze                   | MADR (Markdown Architecture Decision Records) convention |
| **Agent**                                       | An AI instance spawned by Claude Code's `Agent` tool, given a role-specific system prompt and context. Executes a defined task (e.g., BA analysis, TechLead design) and produces artifact files. Not the same as "Claude" — the agent is a child process within Claude Code. | Sub-agent, Orchestrator, Role Agent             | Project-specific                                         |
| **Artifact**                                    | A file written to disk by an agent that represents the output of that agent's work. All artifacts in Virtual Team Skill are Markdown (`.md`) or source code files. Examples: `user-stories.md`, `architecture.md`, `test-plan.md`.                                           | Artifact Group, Required Section                | Project-specific                                         |
| **Artifact Group**                              | The set of artifact files produced by a single role agent for a given project. Example: BA Artifact Group = {`requirements.md`, `user-stories.md`, `acceptance-criteria.md`, `business-rules.md`}.                                                                           | Agent, Artifact                                 | Project-specific                                         |
| **BA** (Business Analyst)                       | The virtual team role responsible for analyzing requirements, writing user stories, defining acceptance criteria, and documenting business rules. Also used as shorthand for the BA Agent and BA Artifact Group.                                                             | User Story, Acceptance Criteria, Business Rules | Industry standard                                        |
| **BDD** (Behaviour-Driven Development)          | A development methodology that expresses requirements and tests using Given/When/Then format, bridging business and technical language. Used in this skill for acceptance criteria (BA) and test case derivation (Tester).                                                   | GWT, Acceptance Criteria                        | Dan North / BDD community                                |
| **BE Dev** (Backend Developer)                  | The virtual team role responsible for generating server-side code: API routes/controllers, database schema/ORM models, migration files, and business logic. Model: `claude-sonnet-4-6`.                                                                                      | FE Dev, API Contract, Tech Stack                | Industry standard                                        |
| **Blocker**                                     | The highest severity level for a cross-agent flag. A Blocker flag indicates an issue that, if unresolved, will prevent the artifact from being used as intended (e.g., fundamental contradiction in requirements).                                                           | Flag, Major, Minor                              | Project-specific                                         |
| **BR-{n}**                                      | Business Rule identifier (e.g., BR-01, BR-002). A uniquely numbered, testable statement that governs system behavior, written by the BA agent in `business-rules.md`.                                                                                                        | Business Rule, BA Phase                         | Project-specific                                         |
| **Business Rule**                               | A precisely stated, testable constraint or logic rule that governs how the system behaves. Format: "The system shall {testable condition}". Example: "BR-01: A user story must have a unique US-{n} identifier."                                                             | BR-{n}, BA Phase                                | Industry standard                                        |
| **Claude Code**                                 | Anthropic's official CLI and IDE extension for interacting with Claude AI. The execution environment for Virtual Team Skill. Provides native tools: Agent, Read, Write, Glob, Grep, TodoWrite.                                                                               | Agent tool, TodoWrite, Skill                    | Anthropic                                                |
| **Compliance Check**                            | A QA/QC review step that verifies process adherence: milestone gates passed, ADRs present for major decisions, security scan complete, cross-artifact consistency verified. Output: `compliance-check.md`.                                                                   | QA/QC Phase, Gate, Sign-off                     | Project-specific                                         |
| **Context Chain**                               | The mechanism by which each agent reads file artifacts from all preceding agents before generating its own output. Ensures coherence across the pipeline. Defined context dependencies are: BA→TechLead→PM→BE→FE→Tester→QA/QC.                                               | Context Dependency Map, Artifact, Pipeline      | Project-specific                                         |
| **Context Window**                              | The maximum number of tokens an LLM can process in a single call (input + output combined). For very large projects, QA/QC and TechLead agents reading all artifacts may approach context window limits.                                                                     | Context Chain, LLM, Agent                       | Anthropic/LLM terminology                                |
| **Cross-agent Flag**                            | A FLAG-{ROLE}-{n} entry written by an agent when it detects a logic error, inconsistency, or missing information in a preceding agent's artifacts. See also: Cross-agent Verification Layer.                                                                                 | FLAG-{ROLE}-{n}, Flags Summary, Layer 2         | Project-specific                                         |
| **Design Freeze**                               | Milestone Gate 1 — declared after TechLead phase completes. Architecture is considered stable; any changes after this point require a new ADR.                                                                                                                               | Milestone Gate, Gate 1, TechLead Phase          | Hybrid Agile+Waterfall                                   |
| **ERD** (Entity Relationship Diagram)           | A diagram showing data entities, their attributes, and relationships between them. In this skill, ERDs are written in Mermaid syntax (`erDiagram` in Mermaid) and stored in `team/techlead/ERD.md`.                                                                          | Mermaid, TechLead Phase                         | Database design standard                                 |
| **FE Dev** (Frontend Developer)                 | The virtual team role responsible for generating client-side code: UI components, pages, API integration services, and state management. Model: `claude-sonnet-4-6`.                                                                                                         | BE Dev, API Contract, Tech Stack                | Industry standard                                        |
| **FLAG-{ROLE}-{n}**                             | Cross-agent flag identifier. Format: `FLAG-TECHLEAD-001`, `FLAG-TESTER-002`. Uniquely identifies a flag raised by a specific agent.                                                                                                                                          | Cross-agent Flag, Layer 2                       | Project-specific                                         |
| **Flags Summary**                               | A file (`projects/{slug}/flags-summary.md`) aggregating all cross-agent flags from all agents in a pipeline run, produced in full-auto mode.                                                                                                                                 | Cross-agent Flag, Flags from Previous Agents    | Project-specific                                         |
| **Flags from Previous Agents**                  | A required Markdown section (`## Flags from Previous Agents`) in each agent's primary artifact. Contains cross-agent flags or "No flags detected".                                                                                                                           | Cross-agent Flag, FLAG-{ROLE}-{n}               | Project-specific                                         |
| **FR-{n}** (Functional Requirement)             | A numbered functional requirement (e.g., FR-01, FR-42). Written as a "shall" clause. See §3.2 for the complete list.                                                                                                                                                         | SHALL clause, GWT stub                          | IEEE 830-1998                                            |
| **Full-auto Mode**                              | The pipeline execution mode triggered by `/team "{requirement}"`. All 7 agents run automatically without operator intervention (unless a hard stop occurs).                                                                                                                  | Per-agent Mode, Pipeline, Hard Stop             | Project-specific                                         |
| **Gate** (Milestone Gate)                       | A defined checkpoint in the workflow where one phase is declared complete before the next begins. Three gates in v1: Gate 1 (Design Freeze), Gate 2 (UAT Readiness), Gate 3 (Release Sign-off).                                                                              | Design Freeze, UAT Readiness, Release Sign-off  | Hybrid Agile+Waterfall                                   |
| **GWT** (Given / When / Then)                   | A three-part format for writing acceptance criteria and test cases: Given {precondition}, When {action}, Then {expected outcome}. Adapted from Behaviour-Driven Development (BDD).                                                                                           | Acceptance Criteria, Test Case, BDD             | Dan North / Gherkin                                      |
| **Hard Stop**                                   | A pipeline termination event triggered after 3 consecutive validation failures for a single agent. The pipeline halts, a failure log is written, and the operator is notified with the specific command to investigate and resume.                                           | Layer 1, Retry, Validation Error Log            | Project-specific                                         |
| **Hybrid Agile + Waterfall**                    | The workflow model used by Virtual Team Skill: sprint-based agile execution within phases, with Waterfall-style milestone gates at key phase transitions.                                                                                                                    | Sprint, Gate, Waterfall, Agile                  | Industry standard                                        |
| **Layer 1 Validation**                          | Automated structural completeness check. After each agent writes its artifacts, the skill checks that all required section headings are present. If not: auto-retry up to 3 times; then hard stop.                                                                           | Validation Layer 1, Required Section, Hard Stop | Project-specific                                         |
| **Layer 2 Verification**                        | Cross-agent logic verification. Each agent reads preceding artifacts and flags any detected logic errors, inconsistencies, or missing information in its `## Flags from Previous Agents` section.                                                                            | Cross-agent Flag, FLAG-{ROLE}-{n}               | Project-specific                                         |
| **LLM** (Large Language Model)                  | The AI model underlying each agent. Virtual Team Skill uses three: `claude-opus-4-8` (TechLead, QA/QC), `claude-sonnet-4-6` (BA, BE Dev, FE Dev, Tester), `claude-haiku-4-5` (PM).                                                                                           | Agent, Model Assignment                         | Anthropic                                                |
| **Mermaid**                                     | A text-based diagramming syntax embedded in Markdown code fences (` ```mermaid `). Used for architecture diagrams, ERDs, and sequence diagrams in TechLead artifacts. Compatible with VS Code (with extension), GitHub, GitLab, Notion.                                      | ERD, Sequence Diagram, Architecture Diagram     | Mermaid.js (mermaid.js.org)                              |
| **Milestone Gate**                              | See **Gate**                                                                                                                                                                                                                                                                 | —                                               | —                                                        |
| **NFR-{n}** (Non-Functional Requirement)        | A numbered non-functional requirement (e.g., NFR-01). Defined using ISO/IEC 25010 quality characteristics and expressed as a Quality Attribute Scenario. See §3.3 for the complete list.                                                                                     | ISO/IEC 25010, Quality Attribute                | IEEE 830-1998 / ISO 25010                                |
| **Operator**                                    | The human user who invokes Virtual Team Skill. One of: Solo Developer (ACTOR-01), Technical Lead (ACTOR-02), PM/BA Human (ACTOR-03), or Startup Founder (ACTOR-04). Not to be confused with the AI agents.                                                                   | ACTOR-01 to ACTOR-04                            | Project-specific                                         |
| **Orchestrator**                                | The master skill (`team.md` or equivalent) that coordinates the pipeline — spawning agents in order, validating artifacts, and managing the context chain. Not itself an agent — it is the skill execution layer.                                                            | Pipeline, Agent, Skill                          | Project-specific                                         |
| **Per-agent Mode**                              | The pipeline execution mode where operators invoke individual agents using role-specific commands (`/team-ba`, `/team-techlead`, etc.) and inspect artifacts between steps.                                                                                                  | Full-auto Mode, Pipeline                        | Project-specific                                         |
| **Pipeline**                                    | The ordered sequence of agent invocations: BA → TechLead → PM → BE Dev → FE Dev → Tester → QA/QC.                                                                                                                                                                            | Context Chain, Full-auto Mode, Orchestrator     | Project-specific                                         |
| **PM** (Project Manager / Scrum Master)         | The virtual team role responsible for sprint planning, task breakdown, story point estimation, and workflow coordination. Uses TodoWrite for live tracking. Model: `claude-haiku-4-5`.                                                                                       | Sprint, Story Point, TodoWrite                  | Industry standard                                        |
| **PR Description** (`pr-description.md`)        | An artifact file generated by BE Dev and FE Dev agents describing the pull request for the generated code: title, summary, list of changes, testing notes.                                                                                                                   | BE Dev Phase, FE Dev Phase                      | Industry standard                                        |
| **QA/QC** (Quality Assurance / Quality Control) | The virtual team role responsible for reviewing all pipeline artifacts, checking compliance, and issuing advisory sign-off. Model: `claude-opus-4-8`.                                                                                                                        | Sign-off, Quality Report, Compliance Check      | Industry standard                                        |
| **Quality Report** (`quality-report.md`)        | A QA/QC artifact listing all issues found across all pipeline artifacts, organized by severity (Critical / Major / Minor).                                                                                                                                                   | QA/QC Phase, Sign-off                           | Project-specific                                         |
| **Release Sign-off**                            | Milestone Gate 3 — the QA/QC agent's advisory verdict (APPROVED / CONDITIONAL / REJECTED) issued at the end of the pipeline. The operator has final authority.                                                                                                               | Gate 3, Sign-off, QA/QC Phase                   | Hybrid Agile+Waterfall                                   |
| **Required Section**                            | A mandatory heading that must appear in a specific artifact file, as defined in the agent's validation schema. Used by Layer 1 Validation. Example: `## User Stories` is a required section in `user-stories.md`.                                                            | Layer 1 Validation, Validation Schema           | Project-specific                                         |
| **Role Agent**                                  | One of the seven specialized AI agents: BA, TechLead, PM, BE Dev, FE Dev, Tester, QA/QC. Distinct from sub-agents.                                                                                                                                                           | Agent, Sub-agent                                | Project-specific                                         |
| **Shall Clause**                                | A requirement statement written using "shall" to indicate a mandatory behavior: "The system shall {behavior}". Per IEEE 830, "shall" = mandatory; "should" = optional; "may" = permissive.                                                                                   | FR-{n}, IEEE 830                                | IEEE 830-1998                                            |
| **Sign-off** (`sign-off.md`)                    | The QA/QC artifact containing the advisory verdict (APPROVED / CONDITIONAL / REJECTED), date, conditions list, and issues list.                                                                                                                                              | QA/QC Phase, Release Sign-off, Gate 3           | Project-specific                                         |
| **Slug**                                        | A kebab-case identifier for a project, chosen by the operator. Used to isolate all artifacts: `projects/{slug}/team/`. Example slugs: `todo-v1`, `my-ecom-mvp`, `auth-service-2`.                                                                                            | Multi-project Isolation, Project                | Project-specific                                         |
| **Sprint**                                      | A fixed-length iteration (default: 2 weeks) in which a subset of user stories are planned for implementation. Defined by PM agent in `sprint-plan.md`.                                                                                                                       | Sprint Plan, Story Point, PM Phase              | Agile / Scrum                                            |
| **Sprint Plan** (`sprint-plan.md`)              | A PM artifact organizing user stories into numbered sprints with goals, story lists, and task assignments.                                                                                                                                                                   | PM Phase, Sprint, Story Point                   | Agile / Scrum                                            |
| **SRS** (Software Requirements Specification)   | A formal document following IEEE 830 standard, produced by the sr:generate skill. Not produced by Virtual Team Skill — Virtual Team Skill produces development artifacts.                                                                                                    | IEEE 830, SRS Workflow                          | IEEE 830-1998                                            |
| **SRS Workflow**                                | The existing pipeline in this repository: sr-brainstorm → sr-spec → sr-plan → sr-generate → sr-validate → sr-improve → sr-save. Produces formal SRS documents. Virtual Team Skill is a separate skill set that can consume SRS outputs.                                      | sr-brainstorm, sr-spec, spec.md                 | Project-specific                                         |
| **Story Point**                                 | A relative unit of effort estimation assigned to a user story. In this skill: S=1 (simple), M=3 (medium), L=5 (large), XL=8 (very large).                                                                                                                                    | Sprint, PM Phase, Task Breakdown                | Agile / Scrum                                            |
| **Sub-agent**                                   | A child agent spawned by a role agent to perform a deeper or parallel sub-task (e.g., BA spawns a domain research sub-agent). Limited to depth 2 — sub-agents cannot spawn further agents.                                                                                   | Agent, Role Agent, BR-07                        | Project-specific                                         |
| **Tech Stack** (`tech-stack.md`)                | A TechLead artifact documenting the chosen technology for each layer of the system (frontend framework, backend framework, database, infrastructure), with justification and rejected alternatives.                                                                          | TechLead Phase, BE Dev Phase, FE Dev Phase      | Project-specific                                         |
| **TechLead** (Technical Lead / Senior TechLead) | The virtual team role responsible for system architecture, technology selection, ADR authoring, ERD creation, and sequence diagram generation. Model: `claude-opus-4-8`.                                                                                                     | ADR, ERD, Mermaid, Design Freeze                | Industry standard                                        |
| **Test Case**                                   | A single test scenario with ID (TC-{TYPE}-{n}), title, preconditions, steps, input data, and expected output. Organized by type in Tester artifacts: unit (TC-UNIT), integration (TC-INT), e2e (TC-E2E).                                                                     | Tester Phase, GWT, Test Plan                    | Software testing standard                                |
| **Test Plan** (`test-plan.md`)                  | A Tester artifact defining the scope, approach, environments, entry/exit criteria, and UAT readiness assessment (Gate 2) for testing the generated system.                                                                                                                   | Tester Phase, UAT Readiness, Gate 2             | IEEE 829 (Software Test Documentation)                   |
| **TodoWrite**                                   | A Claude Code built-in tool that creates and updates a structured task list visible in the conversation UI. Used by PM agent for sprint task tracking. Entries are session-only (not persisted to disk).                                                                     | PM Phase, Sprint Plan, Claude Code              | Claude Code                                              |
| **UAT Readiness**                               | Milestone Gate 2 — declared after Tester phase completes. Confirms test coverage is sufficient for User Acceptance Testing. Status recorded in `test-plan.md`.                                                                                                               | Gate 2, Tester Phase, Test Plan                 | Hybrid Agile+Waterfall                                   |
| **US-{n}**                                      | User Story identifier (e.g., US-001, US-042). Uniquely identifies a user story in `user-stories.md` and cross-references in `acceptance-criteria.md`.                                                                                                                        | User Story, BA Phase                            | Project-specific                                         |
| **User Story**                                  | A requirement statement in the format "As a {actor}, I want {action} so that {benefit}". Assigned a unique US-{n} ID by the BA agent.                                                                                                                                        | US-{n}, BA Phase, Acceptance Criteria           | Agile / Scrum                                            |
| **Validation Error Log**                        | A file written to `projects/{slug}/validation-errors/{agent}-attempt-{n}.md` on every Layer 1 validation failure. Contains timestamp, agent name, attempt number, found sections, missing sections.                                                                          | Layer 1 Validation, Hard Stop, FR-36            | Project-specific                                         |
| **Validation Schema**                           | The defined list of required section headings for each agent's artifact files, used by Layer 1 Validation to check completeness. Not explicitly defined in this SRS — defined in implementation (see OI-01).                                                                 | Layer 1 Validation, Required Section            | Project-specific                                         |
| **Waterfall Checkpoint**                        | A milestone gate that mimics a Waterfall phase boundary — work in the next phase should not begin until the gate is passed. In Virtual Team Skill: design freeze (Gate 1), UAT readiness (Gate 2), release sign-off (Gate 3).                                                | Gate, Hybrid Agile+Waterfall                    | Industry standard                                        |
| `.env.example`                                  | A file generated by the BE Dev agent listing all environment variables required by the generated backend code, with placeholder values (not real secrets). Used by operators to configure their actual `.env` file.                                                          | BE Dev Phase, FR-24                             | Industry convention                                      |
